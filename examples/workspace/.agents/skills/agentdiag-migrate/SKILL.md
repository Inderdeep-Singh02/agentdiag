# Migrate a Target from another maintenance repository

Bring a Target that another repository already maintains — its prompt files, tool schemas, tests, judging rules and the notes its maintainers kept — into this Workspace as a Target agentdiag can validate and generate Suites for, and run once it has an Adapter and a Connector. Everything here is offline: nothing is driven, no platform is read, and the source repository is read and never written. Every step is marked **code** (run it), **judgement** (decide it and say why in a comment beside what you wrote) or **human** (ask the person and record the answer).

`agentdiag <command> --help` is the reference for every flag. Every command takes `--root <workspace>`, and every command but `registry` takes `--target <slug>`; both are left out below. `<source>` is the source repository's directory for this one Target (its agent or package directory, not the whole repository); `<target dir>` is `.agentdiag/targets/<slug>/`.

## Budgets

- **Maintainer notes last.** There are none to read before step 1: this skill writes them (step 9).
- **One read bundle.** Read the source's prompt files, tool schemas, test files and notes once, in full, before you write anything, and list what you read as a comment at the top of the drafts file.
- **Diff first.** Before `generate` writes and before the commit, `git status` and `git diff` (and `--cached`), and read them.
- **Nothing runs.** No Run, no `sync`, no `--from-connector`: the Target has no Adapter and no Connector yet, and `run --dry-run` refusing by name is the expected end state.

## Steps

1. **judgement** — The identity, from the source's own naming: the slug (lowercase words joined by `-`), `--name` (what its owners call it), `--description` (one sentence: what it does and for whom), and, when the source holds the same persona on another channel (a voice build beside a chat build), `--family` and `--channel`; when the Workspace already exists, run `agentdiag registry` first and reuse a `family` that is already there, reading that sibling's `maintainer_notes.md` before you go on. Done when the four values are written, each with the source file it came from, in the comment block at the top of the drafts file (where the Budgets' read list lives too).
2. **code** — `agentdiag init --target <slug> --name <name> --description "<sentence>" [--family <family> --channel <channel>]`. It writes the Target directory with an Adapter of `kind: pending`, a draft Suite, `judge_notes.md`, `maintainer_notes.md` and the local `redaction.yaml`. Done when it exits 0 and prints the paths and the count of REVIEW lines.
3. **code** — Prompts and tools. Copy every prompt file to `<target dir>/prompts/<name>.md` (the system prompt as `prompts/system.md`; a prompt the source joins from several files becomes one file in the order the source joins them, since the deployed set is the joined text) and every tool schema to `<target dir>/tools/<name>.json`, the shape a request's `tools` list carries. Point the Manifest at them — `prompts: {system: prompts/system.md}` and `tools: {<name>: {schema: tools/<name>.json}}` — in place of the commented blocks. Settle the environments REVIEW line too, from the source's own environments (one block per environment, `protected: true` on each that reaches real users), and delete each `# REVIEW:` line you settle, the `family`/`channel` one when it is there. Done when every pointer names a file under the Target directory and `grep -n 'REVIEW:' <target dir>/manifest.yaml` prints two lines: the Adapter kind's and the Connector's.
4. **judgement** — Each tool's `kind`: `retrieval` for a lookup, `action` for anything that changes state, whatever its name suggests; and a tool's own `side_effects` when one does more than the rest, one of `none` (nothing outside this process changes), `sandboxed` (it writes only to a test system) or `live` (it reaches real users or data). Done when every tool has a kind you can defend in one clause, written as a comment beside it.
5. **judgement** — The source's tests, in its own format: read them and list, for each of the source's tests, the user Turns it sends, the rule or tool it checks, and what a pass means there, in the comment block at the top of the drafts file. Then write `<target dir>/drafts/<suite>.yaml` in the shape the `agentdiag-generate` skill describes: one draft for each of the source's tests, `provenance` the prompt section (`prompt:system#<heading>`) or tool (`tool:<name>`) it exercises, spelled as that skill's step 1 says (one markdown heading is one section, its heading slugged; a numbered list inside a heading is one section), the literal Turns, the Evals that pass only when the rule holds (that skill's table "Which Eval for which rule"), and the source's test id in `notes` so a reader can find it again. One of the source's tests whose expectation no mechanical Eval can state gets `prompt_adherence` with the expectation as the rule in `notes`. Keep the source's **correct** expectation, never what the Target does today. Done when every one of the source's tests has a draft, or a comment saying why none (one that tests the platform, not the Target).
6. **human** — Two of the source's tests that disagree, or one that contradicts the prompt, is the person's call: ask which wins, and record the question and the answer as a comment above the drafts it decides. Done when every conflict has a recorded answer.
7. **code** — Mark `init`'s sample Suite retired in the Manifest (`{path: suites/sample.yaml, status: retired}`) or delete it and its line, so the one `generate` write refreshes the Targets table with the Suites as they will stay; then `agentdiag generate --from <target dir>/drafts/<suite>.yaml --check`, fix what it names, then the same without `--check`: it writes `suites/<suite>.yaml` and adds it to the Manifest. Done when `generate` exits 0 with no warning.
8. **judgement** — Judging rules: what the source tells its reviewers about judging this Target (false fails to disregard, conventions a Judge cannot learn from the prompt) goes into `judge_notes.md`, in general terms, at most 600 words; it reaches every Judge prompt verbatim. Check this Workspace's Judge model (`agentdiag run --help`, `--judge-model`) against the Target's, not the source reviewers' Judge, and say so there when they are the same. A rule for the Target stays in its prompt. Done when the notes hold only what a Judge must know.
9. **judgement** — Maintainer facts: what the source's maintainers wrote for themselves (what it does, who it serves, its environments and which reach real users, the traps a previous cycle fell into, where its evidence is kept and how it is read) goes under the five headings of `maintainer_notes.md`, at most 600 words. Name each environment and what it reaches; its settings stay in the Manifest, and a credential is named by its variable, never its value, here or anywhere. Done when each heading holds its facts or `none known`.
10. **code** — `agentdiag validate` until it prints `0 errors`; the warnings it keeps are the pending Adapter and `2 lines marked REVIEW` (the Adapter kind's and the Connector's), which this skill does not settle. Done when those are the only warnings.
11. **code** — `agentdiag registry --write`, then `agentdiag run --dry-run`: the first lists the Target in `AGENTS.md`'s Targets table; the second refuses naming the pending Adapter, which is the expected end state. Done when the table has the Target's row and the refusal reads `adapter.kind: pending`.
12. **code** — Commit the Target directory and every root file `init` and `registry --write` wrote (`git status` lists them), together, diff first. Done when one commit holds them.

## What stays in the source repository

- **Its fix history.** A Change record closes only through `compare` (ADR-0012 §4, the gate): a fix verified elsewhere has no baseline Run, no verifying Run and no comparison here, so it cannot be `verified` or `refuted` under the gate, and a record imported as closed would be one nothing here supports. A history kept in another shape is not imported (ADR-0012 §6). Name the source's history under "Where evidence lives" in `maintainer_notes.md` and leave it there; whether agentdiag should import closed records is an open decision (ticket 51), not this skill's.
- **Its Adapter and Connector.** The two REVIEW lines are settled with the `agentdiag-discover` skill once the platform's plugin is installed: `--from-connector` reads the deployed set and `sync` fingerprints it.
- **Its credentials.** A Manifest names an environment variable; the person sets its value in `~/.agentdiag/env`.

## Done when

1. `agentdiag validate` prints `0 errors`, and its only warnings are the pending Adapter and `2 lines marked REVIEW` (the Adapter kind's and the Connector's);
2. every one of the source's tests has a Scenario in `suites/<suite>.yaml` under a `# from prompt:…` or `# from tool:…` line, or a comment in the drafts file saying why not;
3. `judge_notes.md` and `maintainer_notes.md` are filled, each under 600 words, with no credential value;
4. `AGENTS.md`'s table lists the Target, and `run --dry-run` refuses naming the pending Adapter.
